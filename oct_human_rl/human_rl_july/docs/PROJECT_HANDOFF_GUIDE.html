1. Executive overview

A research simulator for adaptive coordination

The project studies how an AI coordinator can choose the next warehouse task and assign it to an AI or simulated human partner while orders arrive, priorities differ, deadlines tighten, and human behavior changes.

6
Tasks per order

Pick item and fetch box, followed by packing, labeling, weighing, and dispatch.

10
Human profiles

Five training profiles and five completely held out evaluation profiles.

4
Policy choices

PPO, Greedy, Static, and Random coordinators.

6
Priority presets

Random, urgent, medium, routine, urgent first, and urgent later.

41
Automated tests

Environment, model, statistics, dashboard, and scenario coverage.

3
Dashboard workloads

One, two, or three concurrent orders.

3. System architecture

How the components work together

Browser dashboardCollects scenario choices and renders controls, metrics, orders, workers, explanations, and evidence.
Flask applicationValidates requests, manages the active session, selects a policy, advances steps, and serializes state.
Coordination coreCombines the environment, policy, Human Observer, episode tracker, reward model, and legality mask.
Saved artifactsLoads the trained checkpoint, evaluation JSON, research evidence, training logs, and plots.

One simulation step

1
Read current stateThe coordinator receives the enhanced observation and the environment information dictionary, including the legal action mask.
2
Select a legal actionThe policy chooses a task and worker pair or WAIT. The environment owns legality so policy and simulator cannot disagree.
3
Apply the assignmentA pending eligible task starts, an allowed active task may be reassigned, or current work is preserved.
4
Advance every workerHuman and AI workers progress simultaneously. Completed tasks unlock their dependents.
5
Score the outcomeThe environment applies task rewards, deadline effects, parallel work bonuses, avoidable idle penalties, and reassignment cost.
6
Update observer and metricsHuman behavior history, episode counters, CES inputs, logs, and explanations are updated.
7
Render stateThe API returns JSON and the browser refreshes all live panels without reloading the page.

API surface

Priority and deadline behavior

Order priority ranges from 0.20 to 1.00. Higher priority produces a tighter deadline. Orders arrive five steps apart, so the coordinator may need to switch attention when later work becomes urgent.

Why the dashboard can appear quiet after step two Pick item and Fetch box may already be active. The ready queue is then empty because packing requires both to finish. WAIT is correct in that state, and active worker progress continues on every tick.

Observation and action dimensions

BlockFeaturesExamples
Each task6Status, difficulty, assignee, order priority, deadline slack, arrival state
Each worker6Busy, waiting, progress, observed speed, observed error rate, fatigue

For the trained default scenario with two orders, one AI, and one human, the policy receives 92 inputs and selects from 25 actions. There are 24 task and worker assignments plus WAIT.

Policy behavior

PolicyBehavior
PPOUses a trained neural policy with masked actions. The saved model supports the default two order, one AI, one human shape.
GreedyRanks ready tasks using priority, slack, and dependency value, then selects the fastest estimated free worker.
StaticUses fixed task order and rotating worker assignment. It does not adapt to observed human behavior.
RandomSelects a random legal fresh assignment. It waits when no free worker and ready task pair exists.

5. Human Observer

How human variability becomes policy input

The policy is not given a profile label. It observes behavior through worker state and a rolling feature block. This keeps the held out partner test meaningful inside the simulator.

Simulated behavior axes

AxisEffect in the simulator
SpeedChanges the time required to complete a task.
Error rateMay add redo time to the current task.
FatigueAccumulates during work and slows later progress.
Response latencyCreates a delay between assignment and work start.
Speed jitterAdds task level pace variation.
StrategyChanges relative pace on easier and harder work.

Five observer features per human

FeatureMeaning
Smoothed speedRolling mean of observed pace over the recent behavior window.
Smoothed error rateRolling mean of observed errors.
Completion ratioObserved completions divided by observed assignments.
Speed trendDifference between the newer and older halves of recent pace history.
Completed workloadObserved human completions divided by total tasks in the scenario.
Dashboard transparencyThe exact values are displayed with sample and assignment counts.

6. Dashboard operation

How to run and interpret a live episode

  1. Select a policy. Choose PPO, Greedy, Static, or Random. A selection change resets the episode.
  2. Select a partner. Training and held out profiles are grouped and labeled.
  3. Select workload and team. Choose one to three orders and one of the available team compositions.
  4. Select order priority. Use routine, urgent, mixed, or random conditions.
  5. Inspect the initial state. Check order priorities, deadlines, ready Pick item and Fetch box tasks, workers, and the sequencing explanation.
  6. Advance the episode. Step advances one tick, Step times five advances five ticks, and Run continues until paused or complete.
  7. Interpret progress. Task nodes show ready, blocked, active, responding, or complete. Inner bars show task execution progress.
  8. Review the outcome. The completion status reports CES, reward, tasks, orders, and whether the step limit was reached.

9. Failure guide

When the project can break and how to recover

SymptomLikely causeRecovery
Browser cannot connectThe Flask server is not running, crashed, or started in a different folder.Activate the environment, run python app.py, and confirm port 5000.
Port 5000 is already in useA previous server instance or another application owns the port.Stop the existing listener or change the Flask port in app.py.
Import error at startupDependencies were not installed in the active Python environment.Run pip install -r requirements.txt and verify the active interpreter.
PPO fallback noticeThe selected order or team shape does not match the trained checkpoint, or the checkpoint is missing.This is controlled behavior. Use two orders with one AI and one human for PPO, or retrain for the desired shape.
Research cards unavailableevaluation.json or research_evidence.json is missing, malformed, or incompatible.Restore the bundled result files or rerun evaluation. Live simulation can still operate.
No ready tasks after early stepsPick item and Fetch box are both active and later work is dependency blocked.Inspect active worker progress and continue stepping. This is usually expected.
Step limit reachedA slow or erratic partner, static ordering, errors, or high workload consumed the available ticks.Review the event log and worker performance. Reset with another policy or scenario.
Dashboard displays old wordingThe browser cached an earlier page.Use Ctrl F5 or clear the site cache.
ZIP does not extractAn obsolete archive created with the earlier packaging method was used.Use the corrected 29.1 MB native Windows ZIP with the validated hash.
One user's reset changes another viewThe server has a single process global session.Use one user at a time or implement isolated persistent sessions.
State disappears after restartEpisode state is stored only in memory.Expected behavior. Add a database or serialized session store for persistence.
Model load is slowPyTorch initialization and checkpoint loading can take several seconds on first use.Wait for the request to finish and avoid repeated reset clicks.
Do not expose the bundled Flask server directly to the internet It has no authentication, tenant isolation, rate limiting, production process manager, transport security configuration, or hardened deployment settings.

10. Current limitations

What is not possible in the current version

The items below are not impossible in principle. They are simply not implemented or validated in the current prototype.

CapabilityCurrent statusWhat would be required
Production deploymentNot implemented
No hardened server, authentication, database, monitoring, or operational support model.		Production WSGI service, reverse proxy, TLS, secrets, access control, logging, monitoring, backups, and deployment automation.
Independent multiuser sessionsNot implemented
All users share one in memory episode.		Session identifiers, persistent state, concurrency control, and tenant isolation.

The saved PPO checkpoint supports two orders, one AI, and one human.		Separate checkpoints per shape or a variable size architecture followed by retraining and evaluation.
Real warehouse controlNot implemented
No connection to robots, scanners, warehouse systems, sensors, or safety controllers.		Hardware adapters, event ingestion, command protocols, safety interlocks, simulation to reality validation, and operational certification.
Real human behavior inferenceNot validated
All people are simulated profiles.		Ethically approved data collection, privacy controls, bias assessment, consent, calibration, and field studies.
Guaranteed optimal scheduleNot guaranteed
PPO and heuristics choose actions but do not prove global optimality.		An exact optimization formulation, bounded problem size, solver integration, and optimality analysis.
Causal AI explanationsLimited
Current explanations summarize observable inputs and operational logic.		Validated attribution methods, counterfactual tests, and explanation quality studies.
Live training in the dashboardNot implemented
The UI loads a saved checkpoint.		Job management, progress streaming, resource limits, checkpoint registry, cancellation, and result tracking.

11. Recommended roadmap

A practical path beyond the prototype

  1. Stabilize the application boundary. Move simulation state out of the global process variable, add per user sessions, structured logs, configuration files, and error monitoring.
  2. Build a production service layer. Add authentication, authorization, database persistence, a production WSGI server, deployment automation, and health checks.
  3. Generalize the learned coordinator. Choose either a checkpoint registry for supported shapes or a graph based policy that handles variable workers and orders. Retrain and reevaluate.
  4. Add reproducible experiment management. Record scenario configuration, seed, checkpoint version, code version, metrics, and artifacts for every run.
  5. Create integration contracts. Define safe inbound events and outbound recommendations before connecting any warehouse system.
  6. Run human centered validation. Evaluate usability, explanation quality, bias, workload, privacy, and appropriate human override mechanisms.
  7. Introduce shadow mode. Compare recommendations against real operations without allowing the system to control equipment or assign people.
  8. Conduct a controlled pilot. Proceed only after safety, security, legal, and statistical review.

Suggested priority

PhaseFocusExit condition
Phase 1Reliability, session isolation, persistence, deploymentMultiple users can run independent reproducible episodes safely.
Phase 2Variable shape policy and experiment registryEvery supported scenario has a trained, versioned, evaluated policy.
Phase 3Integration simulator and shadow dataExternal events are ingested without controlling real operations.
Phase 4Human factors, safety, security, and pilotFormal approval and monitored pilot criteria are satisfied.
Recommended next technical milestone Implement isolated persistent sessions and a checkpoint registry before adding more dashboard features. Those foundations remove the largest reliability and model compatibility constraints.

Responsible use checklist

  • Present results as simulation evidence only.
  • Keep live episode demonstrations separate from saved repeated evaluations.
  • Do not infer real employee ability, intent, health, or productivity from simulated profiles.
  • Do not connect the prototype to operational equipment without safety engineering and approval.
  • Do not expose the development server directly to untrusted networks.
  • Label Greedy fallback behavior whenever PPO dimensions are incompatible.
  • Retain code, checkpoint, configuration, and seed information with every published result.
